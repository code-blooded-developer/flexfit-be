# CLAUDE.md — FlexFit Backend Guidelines

## Project Overview
FlexFit is a personalized fitness tracking and automated workout generation REST API built with **Spring Boot 4.0.3** and **Java 21**, backed by **PostgreSQL** and **Spring Data JPA**.

---

## Commands

### Build & Run
- **Build**: `./mvnw clean install`
- **Compile**: `./mvnw compile`
- **Run local server**: `./mvnw spring-boot:run`
- **Run tests**: `./mvnw test`
- **Single test**: `./mvnw test -Dtest=ClassName#methodName`

```

├── Application.java              # Main Spring Boot entry point
├── config/                       # SecurityConfig (JWT filter, CORS, BCrypt)

├── dto/

├── exception/                    # GlobalExceptionHandler & custom exceptions
├── repo/                         # Spring Data JPA repositories
├── security/                     # JwtUtil, JwtAuthenticationFilter, CustomUserDetailsService
├── seeder/                       # EquipmentSeeder & ExerciseSeeder (CommandLineRunner)
├── service/                      # Business interfaces
│   └── impl/                     # Service implementations with @Transactional
├── util/                         # UnitConversionUtil (metric/imperial conversions)
└── validator/                    # Custom Jakarta Bean Validation annotations/validators
```

## Code Style & Architectural Conventions

### 1. API & Controllers
- All REST endpoints are prefixed with `/api/v1`.
- Controllers must return `ResponseEntity<ApiResponse<T>>`.
- Always wrap response data with `ApiResponse.success(data)` or `ApiResponse.success(message, data)`.
- Authenticated user ID is stored as a `UUID` in `SecurityContextHolder`:
  ```java
  UUID userId = (UUID) SecurityContextHolder.getContext().getAuthentication().getPrincipal();
  ```
- Use Jakarta validation annotations (`@Valid`, `@NotNull`, `@NotBlank`, etc.) on `@RequestBody` parameters.

### 2. Service Layer
- Interfaces live in `com.harish.flexfit.service` and implementations live in `com.harish.flexfit.service.impl`.
- Annotate service classes with `@Service` and `@Slf4j`.
- Use `@Transactional` on mutating methods and `@Transactional(readOnly = true)` on read-only methods.
- Log method entries and significant state mutations with descriptive log messages (`log.info(...)`).

### 3. Entities & Database
- Primary keys must be UUIDs generated by Hibernate:
  ```java
  @Id
  @GeneratedValue
  @Column(columnDefinition = "uuid", updatable = false)
  private UUID id;
  ```
- Use `@CreationTimestamp` on `createdAt` and `@UpdateTimestamp` on `updatedAt`.
- Use Lombok annotations (`@Data`, `@Builder`, `@NoArgsConstructor`, `@AllArgsConstructor`) appropriately.
- Persist metric units in the database (`heightInCm`, `weightInKg`) while allowing user input in preferred units.

### 4. Authentication & Security
- Authentication is stateless via JWT tokens passed in HttpOnly secure cookies:
  - `ACCESS_TOKEN` (default 30 min expiration)
  - `REFRESH_TOKEN` (default 7 days expiration)
- Passwords must be hashed with `BCryptPasswordEncoder`.
- Public endpoints: `/api/v1/auth/**`, `/api/v1/health`, `/actuator/**`. All other routes require authentication.

### 5. Error Handling
- Throw domain runtime exceptions:
  - `ResourceNotFoundException` (HTTP 404)
  - `BadRequestException` (HTTP 400)
  - `ConflictException` (HTTP 409)
- All exceptions are captured by `GlobalExceptionHandler` and returned as `ApiResponse.error(message)`.

## Core Domain Logic & Rules

### Workout Generation Engine (`WorkoutServiceImpl`)
- **Workout Splits**: `FULL_BODY` (1-day), `UPPER_LOWER` (2-day), `PUSH_PULL_LEGS` (3-day), `BRO_SPLIT` (5-day). The day's target muscles are determined by `(workoutCount % splitLength)`.
- **Equipment Compatibility**: Exercises are strictly filtered against user-owned equipment (`UserEquipment`).
- **Experience Level Gating**:
  - `BEGINNER` $\rightarrow$ Beginner exercises only.
  - `INTERMEDIATE` $\rightarrow$ Beginner + Intermediate exercises.
  - `ADVANCED` $\rightarrow$ All difficulty levels.
- **7-Day Exercise Exclusion**: Exercises performed in the last 7 days are excluded from auto-generation to maintain variety.
- **Workout Structure**:
  1. Cardio Warmup (1 exercise, duration based on `FitnessGoal`).
  2. Targeted Warmup (4 exercises matching the session's target muscles).
  3. Main Exercises (time-budgeted distribution across muscles, balanced compound/isolation ratio, goal-based sets/reps/rest).
  4. Cooldown Stretches (4 exercises targeting the worked muscles).
- **Alternatives & Replacements**: Alternative exercises (`GET /api/v1/workouts/{workoutId}/alternatives`) must prioritize the workout's target muscle first (Primary match $\rightarrow$ Secondary match $\rightarrow$ Others), sorted alphabetically within ranks.
- **Workout Swap Workflow**:
  - `GET /api/v1/workouts/today/alternate-muscles?currentMuscle=...` returns alternate split/muscle options excluding the current muscle.
  - `POST /api/v1/workouts/today/swap` accepts `SwapWorkoutRequest` with the selected `muscle` and regenerates today's uncompleted workout for that target muscle group.
